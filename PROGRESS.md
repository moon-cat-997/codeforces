| 2026-08-19 | 1538C Number of Pairs | 1300 | binary search (boundary counting) | **Ladder B #5, the longest debug in the log (four rewrites), and the first *hand-rolled* boundary search — every earlier rep used the STL or searched an answer space.** Sort, fix `a[i]`, and the partners form a contiguous block: `l - a[i] ≤ a[j] ≤ r - a[i]`, so the count is a difference of two positions ⇒ O(n log n). The *idea* took minutes; the **implementation was the entire problem**, which is a real and distinct category from "find the trick". Four bugs, found one at a time, each masking the next: (1) a `while (lo < hi)` body that assigned only to `mid` — **`lo`/`hi` never moved**, so the loop could not terminate; at `-O0` it hung, but at `-O2` GCC **deleted the loop outright** (an infinite loop with no side effects is UB), so the symptom was plausible wrong numbers instead of a TLE — actively misleading first evidence. (2) The predicate was the **band** `l ≤ sum ≤ r`, which is `F…F T…T F…F` — *not monotone*, so a `false` says "left or right" and discards nothing; no `lo`/`hi` fiddling can fix a non-monotone predicate, the predicate itself must change. (3) After splitting into two one-sided predicates, each was paired with the **opposite** template — the searches were named `lower`/`upper` and bound to `r`/`l` respectively, i.e. **backwards**, so the templates got chosen by the identifier instead of by the predicate's direction. (4) Finally an off-by-one at the right edge: the primitive computes *first `≥ X`*, so the right end needs `r + 1` (integers: `> r` ≡ `≥ r+1`), and using `r` silently drops every pair summing to exactly `r` — visible as "every answer is short by a little", never as a crash. The unlock was **collapsing to one primitive**: *first index where `P` is true*, `P` monotone `F→T`, on a **half-open** `[lo, hi)` with `hi = n`. Half-open is what lets the search return `n` = "no such element"; the earlier closed `hi = n-1` had no way to express an empty window, which is why it kept needing special cases that could not be made correct. Also `int ans` → `ll` (`n(n−1)/2` passes `INT_MAX` at n ≈ 65 000; here the max answer is ~2·10¹⁰). Residual: `vec<pair<int,int>>` still carries the original index, but `.second` is never read — a plain `vec<int>` halves the memory. Practical note: in a contest this is `upper_bound(r) - lower_bound(l)`; hand-rolling it once to own the invariant is the point, then use the library. Stress-verified vs brute (1000 random cases) + edges (n=1, two maximal values summing to 2·10⁹, all-equal) + the overflow case (n=2·10⁵, all 1s, `l=r=2` → 19 999 900 000 exactly); n=2·10⁵ in 0.03s vs a 2s limit |

## Habits being reinforced (from reviews)

- Simple beats clever when it's fast enough (158A, 4C).
- Minimize carried state: when order doesn't matter, reach for **counts, not pointers/positions** (158B — solved in 79 lines what counting does in 10).
- Read constraints → derive complexity budget before coding (learned via 4C's n≤1e5).
- Special-judge / "output any valid answer" problems (4B): local exact-diff can false-fail on YES cases — validate output *validity* (constraints + sum), trust CF's checker.
- `"\n"` not `endl`; exact output strings; test self-made edge cases beyond the given samples.
- When a condition is a *guess* (6C's `i==j` vs `n&1`), construct a test that distinguishes the candidates before submitting — for 6C a 3-element hand trace (`[5,1,1]`) was enough to kill `n&1`.
- **Classify the technique by its proof obligation, not its loop shape** (1324D): incremental + invariant + no-backtracking describes greedy, binary search, merge, *and* sliding window alike. The discriminator is whether a **genuine choice** exists — could you have decided differently and still gotten a valid answer? Yes ⇒ greedy, owe an exchange argument or stress test. No, the branch is a fact about the data ⇒ counting/invariant, owe a partition check. See CHEATSHEET "What greedy actually means".
- On a sorted array, ask **"which element can I *completely finish* right now?"** rather than "how do I scan?" — the extremes are never ambiguous (`hi` pairs with everything left, or `lo` pairs with nothing left), which is what turns a drifting pointer with boundary patches into a clean converging loop (1324D).
- A first AC is not the end of a problem: **re-deriving the clean form from understanding** (1324D, 14 lines + 2 guards → 8 lines + 0) is where the pattern actually gets learned.
- **Read the *value* bound, not just `n`** (616D, 546B): when `a_i` is capped by something small, index an array **by the value** instead of reaching for `map`/`unordered_map`. O(1) and cache-friendly vs O(log n) and pointer-chasing — measured 11× on 616D.
- **A guard you can't prove is needed is a bug in waiting** (701C, then 616D — same dead `lo < hi` twice). In the canonical `end`-driven window the shrink condition is *sufficient* on its own. If the urge to add a bounds guard shows up, that's the signal to prove the invariant, not to patch it — the guard doesn't protect you, it converts a loud hang into a silent wrong answer.
- **When the statement gives you a count, consume exactly that many items** (706B: `while (cin >> m)` instead of `rep(i,0,q)`). Reading to EOF is a *different input format* — reserve it for problems that say "read until end of input". Otherwise the loop silently answers phantom queries or swallows the next block, and no compiler warning fires (the count variable *is* assigned, so `-Wunused-variable` stays quiet). Same species as the dead-guard smell: code that happens to be right on this input shape rather than right by construction.
- **Store a range as `(l, r)`, or as two named variables — never reversed** (616D stored `(hi, lo)`). Consistent-but-backwards code is correct today and a WA on a tired evening.
- **Name a predicate for what `true` means** (1873E's `check()` returning "impossible"). A boolean helper whose polarity you must open the body to learn is where off-by-ones live — and it's what forces correction terms like `hi - 1` at the print. `feasible` / `tooExpensive` / `enoughTime` cost nothing and make the search template self-checking.
- **A widening that happens *after* the arithmetic guards nothing** (1873E's `ll mid = lo + (hi-lo)/2` over `int` endpoints). Overflow is decided by the types of the operands, not the type of the destination. Widen the inputs — a half-measure that *looks* defensive is worse than none, because it stops you looking.
- **`lower_bound` locates, `upper_bound` counts** (474B vs 706B — same trap, opposite answers). Counting wants the first element *past* the target; locating wants the first element that *reaches* it. Pick by what the question asks for, not by which name you typed last time — and note the failure is on boundary-equal queries, so a sample built by hand will usually expose it if you actually try both.
- **A binary search that TLEs is almost never slow — it's not terminating** (1613C). First move on any TLE: *count the operations* (multiply the nesting levels: check × iterations × tests) against the ~10⁸/s budget. If the count is trivial, stop profiling and start looking for the loop that never ends — here an `int mid` between `ll` endpoints, truncating past `INT_MAX` to a value outside `[lo, hi)`, after which the assignments stop shrinking the interval. Every variable in the search — `lo`, `hi`, *and* `mid` — takes one type, chosen from the proven answer range. And signed overflow is UB, not "wraps around": the program can't be reasoned about at all after it.
- **A band is not a binary search** (1538C). `l ≤ x ≤ r` is `F…F T…T F…F` — true in the middle, false on *both* sides — so a `false` cannot tell you which half to discard. Any inclusive-range count is **two one-sided searches subtracted**, never one two-sided search. The moment a predicate has an `&&` joining two comparisons in opposite directions, stop and split it.
- **Hand-rolled boundary searches use half-open `[lo, hi)`** (1538C). With a closed `[lo, n-1]` there is no return value meaning *"no such element"* — so an empty window is inexpressible, and you end up bolting `if` cases onto a search that structurally cannot be right. `hi = n` lets the search return `n`, and counts become plain differences of positions with zero special cases. The special cases you keep adding are the *symptom*; the interval convention is the *cause*.
- **Choose the template by the predicate's direction, never by the function's name** (1538C). Write the `T`/`F` row for a small concrete input first — `F→T` ⇒ *first-true* (`hi = mid`, midpoint rounds **down**); `T→F` ⇒ *last-true* (`lo = mid`, midpoint rounds **up**). Better still: phrase **both** edges as `F→T` so only one template exists in the file. For integers `> r` ≡ `≥ r+1`, so any "strictly greater" edge folds into the `≥` primitive.
- **"It printed output" is not evidence that a loop terminates** (1538C). An infinite loop with no observable side effects is *undefined behaviour*, and GCC at `-O2` may delete it — turning a hang into plausible wrong numbers and sending you hunting in the wrong place. When a hand-rolled search misbehaves, first verify that **every path through the body shrinks the interval**, then re-run at `-O0` where a non-terminating loop is loud.
- **Multi-bug debugging is a different activity from single-bug debugging** (1538C, four bugs deep). With more than one fault live, a *correct* fix still leaves the output wrong — so the feedback signal is worthless and the temptation is to revert good work. Fix the one bug you can *prove* is a bug, keep it regardless of whether the output improves, and only then look again. Bisect the bug count before bisecting the logic.
- **Counting pairs ⇒ the counter is `ll`, unconditionally** (1538C). `n(n−1)/2` crosses `INT_MAX` at `n ≈ 65 000`; at `n = 2·10⁵` the answer is ~2·10¹⁰, 10× over. No sample will ever show this — the small answers in the sample block are exactly why it survives local testing and dies on the judge.
- **"It fits in `int`" needs a margin you can state.** 1873E's bound lands at 2·10⁹ against `INT_MAX` 2.147·10⁹ — 7% of headroom, arrived at by luck. When the answer range is a *different* range from the input range, compute it explicitly and pick the type from that, not from `a_i ≤ 10⁹`.
